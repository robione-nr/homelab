## Hermes Gateway and Profile Architecture

Validated Mattermost as the practical human-facing interface to Hermes and confirmed that gateway multiplexing was routing Jeeves into the `liaison` profile rather than merely presenting a different name over the base Hermes workspace. The active liaison environment reported its own `HERMES_HOME`, providing direct evidence of profile isolation.

Named profiles were treated as independent configuration and secret scopes. A profile `.env` was not assumed to inherit automatically from the base profile, and values present in Hermes configuration were also found not to imply that arbitrary subprocesses launched through the terminal tool would receive those values as exported shell variables.

This led to a clearer configuration model: genuinely gateway-wide values belong in service-level environment configuration, while profile-specific credentials and settings remain profile-local.

## Workflow Direction

Mattermost was established as transport/UI, Jeeves as the persistent liaison, and specialist agents as narrowly scoped workers. Durable execution state would move into a Kanban dispatcher rather than living inside long conversational contexts.

The intended loop became: user → Mattermost → Jeeves → Kanban/task state → fresh specialist session → durable artifacts/RAG/memory → next eligible task.

## Result

The architecture separated human interface, persistent liaison identity, gateway routing, specialist execution context, secrets, and durable workflow state. The next major step was proving the Kanban execution loop against real Hermes profiles rather than adding another communication layer.
